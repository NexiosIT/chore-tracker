# Comment Discipline

> Code MUST be self-explanatory. A comment exists only to carry what the code cannot express — a domain constraint, a non-obvious *why*, an invariant, or an external reference. Comments never restate what code does, and never carry traceability: spec→code mapping lives in the Traceability Matrix and `trace.yml`, standards compliance lives in the checkpoint results — neither lives in the code.

## Motivation

Generated code drowns reviewers in comments that describe intent instead of adding information: spec IDs, standard citations, line-by-line narration, doc-comments that echo the signature. Every such comment bloats the diff a human must review, and every fact copied into a comment (a column type, a route, a scenario title) is a second source of truth that silently drifts from its owner. Names, types, and structure explain *what*; comments are reserved for the *why* that code cannot say.

## Rules

1. **Self-explanatory first.** Express intent through names, types, small functions, and structure (STD-003). Before writing any comment, apply the litmus in Rule 9 — the default is *no comment*.

2. **No spec references in code.** Use case IDs (`UC-…`), feature IDs (`FT-…`), screen IDs (`SCR-…`), rule IDs (`R-nn`), scenario titles, and `constraints.md` citations MUST NOT appear in code or comments. The Traceability Matrix and `trace.yml` own the spec→code mapping.

3. **No standard or decision citations in code.** Standard IDs (`STD-…`), decision IDs (`ADR-…`), and rule numbers MUST NOT appear in code or comments. Compliance is recorded in the checkpoint results (`standards_applied`) and the Standards Compliance Report — never in the code itself.

4. **No generation-process residue.** Comments about the process that produced the code — TDD phases, checkpoint numbers, reasoning-trace pointers, "generated by" banners, self-corrections — MUST NOT appear.

5. **No narration.** A comment that restates what the adjacent code visibly does (`// parse the date`, `// call the repository`, `// set up test data`) MUST NOT appear. If a block needs a label, extract a well-named function instead.

6. **No ceremony doc-comments — public API included.** Doc-comments (Javadoc, XML docs, JSDoc, docstrings) on members whose name and signature already say everything (trivial constructors, getters/setters, parameter echoes like `@param repository the repository`) MUST NOT appear — on any member, public or not. A doc-comment passes the same test as any comment: it exists only if it carries something the name and signature cannot.

7. **No duplicated facts.** A fact owned by another artifact MUST NOT be restated in a comment: column types and precision belong to migrations/ORM configuration, wire shapes to the contract, routes to the router/file path, configuration values to config files, test behavior to the tests. Duplicated facts drift.

8. **Justified comments.** A comment is correct when it states, once, at the owning declaration, something the code cannot express:
   - domain semantics the type system cannot carry (*"percentage, not fraction: 20.5 means 20.5%"*),
   - a non-obvious choice (*"DATE, not DATETIME2 — avoids timezone ambiguity"*),
   - an invariant or precondition not expressible in code,
   - a reference to an external issue or vendor bug that forces a workaround.

9. **Litmus test — all three must hold, or the comment is not written:**
   - it would still be true after a good rename or refactor;
   - its source of truth is *this* code, not another artifact;
   - it says *why*, not *what*.

## Examples

### Non-Compliant

```csharp
/// <summary>
/// Domain entity representing a statutory contribution rate.
/// Implements business rule R-01 (constraints.md).           // ← spec reference (Rule 2)
/// Uses decimal for monetary values (STD-024).               // ← standard citation (Rule 3)
/// </summary>
public class ContributionRate
{
    /// <summary>Primary key — auto-generated by EF Core.</summary>   // ← ceremony (Rule 6)
    public int Id { get; set; }

    /// <summary>
    /// Statutory rate as a percentage.
    /// Mapped to DECIMAL(5, 2) in the database schema.       // ← fact owned by ORM config (Rule 7)
    /// </summary>
    public decimal RatePercentage { get; set; }
}
```

```java
// Parse the reference date string                            // ← narration (Rule 5)
// Follows TDD discipline: RED-GREEN-REFACTOR (STD-014)       // ← process residue (Rule 4)
var date = LocalDate.parse(referenceDateString);
```

### Compliant

```csharp
public class ContributionRate
{
    public int Id { get; set; }

    // Percentage, not fraction: 20.5 means 20.5%.
    public decimal RatePercentage { get; set; }
}
```

```java
// Floor lookup: the entry with the greatest effectiveFrom that is <= the reference date.
Optional<ContributionRate> findApplicableRate(LocalDate referenceDate);
```

## Applicability

- **Service types:** all (backend, frontend, gateway)
- **Domains:** all
- **Exceptions (mandated by other standards — these take precedence):**
  - Warning-suppression justifications required by STD-019.
  - Bare `// Arrange` / `// Act` / `// Assert` markers in tests where the stack test standard permits them — three words, no prose.
  - Tooling-mandated lines that are syntactically comments (shebang lines, license headers the hub requires, linter directives that a suppression justification accompanies per STD-019).

## Enforcement

This standard is `injection: workflow` (the same mechanism as STD-014/015/016 and STD-023): its rules are inlined into `/ie/generate`'s mandates rather than loaded as one of the manifest's context standards, and it is therefore **absent from `manifest.standards[]` by design** — that absence is not a missing-file error, and it carries no row in the Standards Compliance Report. Discipline that governs every line written has to be present while the lines are written; a path in a forty-item context list is not.
