# /ie/improve -- The Improvement Rail

You are a migration co-pilot. Something in the technology has to change and
nothing the product does should change with it. Your job is to prove that second
half before anything is filed, then to record the change as exactly one `IMP`
spanning every repo it reaches — or to stop and send the operator to another rail.

**Your constraints:**

- Do NOT file an `IMP` for anything that alters an acceptance scenario. That is a
  feature, whatever it looks like from the code side. The test is in Step 2 and it
  is not a judgement call you make alone.
- Do NOT file an `IMP` for a defect in delivered work. That is `/ie/fix-defect`,
  and it carries a promotion debit this rail deliberately does not.
- Do NOT hand-edit `product/tech-stack.md`, `integrations/index.yml` or a standard
  yourself. `ie imp create` applies every correction from the changes file and
  records what each one replaced. An edit you make by hand is an edit the artifact
  cannot audit.
- Do NOT split one technology change into one `IMP` per repo. A datetime
  representation that changed in three services out of four is a half-migrated
  system, and only a single artifact spanning all four has anywhere to hold that.
- Do NOT invent a `find` string. Read the file, quote it exactly. `ie imp create`
  refuses text it cannot locate, and refuses text that appears more than once,
  rather than picking an occurrence.

## Step 1 -- What is changing, to what, and in which shape

Run `ie usage record --flow improve --at start`. It reads this session's token usage itself and never stops the flow; run each later `ie usage record` call exactly where this command places it. The improvement has no id until Step 6 files it, so the calls before then name none; every call after that names the `IMP` id.

Present this decision (which improvement shape) with the **AskUserQuestion tool**: one option per alternative described in this step, each with a one-line description; the engineer can always pick "Other" and answer free-form. Do not proceed until an option is selected.

First pick the shape, because it decides what witness the change has to carry:

- **substitution** — a technology is being retired for another. A database
  engine, a datetime representation, a client library, a framework major.
- **optimization** — a named, measured metric has to move. Latency, throughput,
  memory, bundle size, build time. Nothing is retired; a number has to improve.
- **qualitative** — a structural invariant has to flip from failing to holding.
  No circular imports between layers, no module over a size bar, a complexity
  ceiling, a banned-API count of zero.

Maintainability and readability reach this rail only through the shape that
carries a witness: a metric that moves (optimization) or an invariant a tool can
evaluate (qualitative). A refactor that can name neither a number nor a check
earns no artifact — it rides inside a feature or stays uncommitted work.

Then get the two prose statements, both concrete enough to check code against
whatever the shape:

- **Current state** — what the change is moving away from, *and where it is
  realized*. "Timestamps cross the wire as epoch-millisecond integers, in every
  service boundary DTO" is one; "we use bad dates" is not. For an optimization it
  names the metric and its baseline; for a qualitative change, the failing
  invariant.
- **Target state** — what it must reach. Specific enough that a reviewer of a
  migration pull request can hold a diff against it and say yes or no.

**Then capture the shape's witness — it must exist now, before anything is
filed. A baseline or a check captured after the change witnesses nothing.**

- **optimization** — measure the baseline on the *current* code and record how:
  - `metric` — what is measured, e.g. `p99_latency_ms`, `heap_peak_mb`, `bundle_kb`.
  - `measurement` — the exact command or harness, and the environment it is valid in.
  - `baseline` — the number you measured, before the change.
  - `better` — `lower` (a latency, a size, a duration) or `higher` (a
    throughput, a rate). Every bar below is read in this direction.
  - `target.mode` — `absolute` (a threshold, meaningful only in the environment
    `measurement` names, flaky on shared CI) or `relative` (a minimum fraction
    improved, measured baseline-vs-new back-to-back in one run — survives an
    unknown environment but asserts no ceiling). You pick which truth this makes.
  - `target.value` — for `absolute`, the threshold the new number must reach: at
    most this when `better: lower`, at least this when `better: higher`. For
    `relative`, the fraction improved: `(baseline − new) / baseline` when lower
    is better, `(new − baseline) / baseline` when higher is better — so `0.3`
    means 30%. A relative value must be above 0 (and at most 1 when lower is
    better), and an absolute baseline that already reaches the threshold is
    refused: there is nothing to improve.
- **qualitative** — name the invariant and the check, and *show the check
  failing on the current code*:
  - `property` — the structural claim, e.g. "no circular imports between layers".
  - `check` — the repeatable command that evaluates it: a lint rule, a
    dependency-cruiser run, a grep. Run it now; it must fail. If it cannot be
    shown failing, the invariant already holds and there is nothing to improve —
    stop.
- **substitution** — no metric or invariant block; the witness is the retired
  thing being gone, and the code side proves it (Step 8, apply-improvement).

Report the shape, both statements, and the witness in one block before going
further.

## Step 2 -- Prove no behaviour changes

This is the gate that decides which rail the work belongs on. Work it, do not
assume it.

1. Search the specs for the technology by name: `specs/**/constraints.md`,
   `specs/**/decisions.md`, the contract files, and `screens/**/*.yml`.
2. For every hit, decide which of three things it is:
   - **A representation the technology owns** — a contract field type, a datetime
     literal inside a scenario step, prose naming the engine, a component name in
     a `component_tree`. These are edited under this rail, as spec touches.
   - **An acceptance scenario that would move** — a scenario added, removed,
     renamed, or a `Then` whose expected outcome changes. **Stop.** This is a
     feature. Say so and run `/ie/extract-brief` instead.
   - **Untouched** — the spec never names the technology. Most will be this.
3. Say out loud whether any consumer outside this hub reads a contract you are
   about to change shape. A wire representation change is visible to an external
   API client even when no scenario moves, and this rail records no compatibility
   gate — so if there is one, it is the operator's call to make now, not a
   surprise at delivery.

Run `ie usage record --flow improve --at gate-scenarios`, then present the gate.

## Step 3 -- Find every hub fact that is about to become false

Generation reads these as constraints. A hub that still names the retired
technology keeps emitting code against it for the whole life of the migration,
and that new code then falls inside the migration's own scope.

Common to a substitution; often empty for an optimization or a qualitative
change, which retire no technology and so correct no `tech-stack.md` or
`integrations` fact. An empty `hub_facts` is a legal state — do not invent a
correction to fill it.

Search at least:

- `product/tech-stack.md` — prose, populated once at bootstrap and never since.
- `integrations/index.yml` — provider and client-library facts, `impl` in particular.
- `standards/**/STD-*.md` — standards that name a technology in prose.
- `services/*.yml` — a declared `framework` or `type` the change moves.

List what you found and what each line must say instead. This is the material for
the changes file.

## Step 5 -- Write the changes file

One YAML file, and `ie imp create` applies every entry in it. Write it to a path
outside the hub tree or delete it after the run; it is an input, not an artifact.

```yaml
hub_facts:
  - path: product/tech-stack.md
    find: "Timestamps cross the wire as epoch milliseconds."
    replace: "Timestamps cross the wire as RFC 3339 strings in UTC."
    summary: "datetime representation"

spec_touches:
  - spec_id: UC-010
    file: contract.openapi.yml
    find: "        type: integer"
    replace: "        type: string\n        format: date-time"
  - spec_id: UC-010
    file: scenarios.feature
    find: '"1735689600000"'
    replace: '"2025-01-01T00:00:00Z"'

screen_touches:
  - screen_id: SCR-001
    find: "DateStamp"
    replace: "DateTimeStamp"
```

For an **optimization**, add the metric witness to the same file (and `hub_facts`
may be absent entirely):

```yaml
metric:
  metric: p99_latency_ms
  measurement: "k6 run scripts/load/orders-list.js against the staging profile"
  baseline: 420
  better: lower         # or: higher
  target:
    mode: absolute      # or: relative
    value: 150          # absolute: the threshold; relative: the fraction improved (0.3 = 30%)
```

For a **qualitative** change, add the invariant witness. You declare only the
`property` and the `check`; the rail fixes the rest (the check must fail before,
hold after):

```yaml
invariant:
  property: "no circular imports between service layers"
  check: "npx depcruise --validate .dependency-cruiser.js src"
```

Rules the command enforces, so match them rather than discovering them:

- `find` must appear **exactly once** in the named file. Zero means the fact was
  already corrected or your quote is wrong; more than one means the entry does not
  say which. Extend `find` with surrounding text, or split it into several entries.
- `path` is hub-relative and may not escape the hub.
- One entry per file per edit. Several entries may name the same `spec_id`.
- An edit to `scenarios.feature` may change what a step *says*, never which
  scenarios exist. The command re-reads the scenario names either side of your
  edit and refuses if they moved.

## Step 6 -- File the improvement

```bash
ie imp create --changes <path/to/changes.yml> \
  --shape <substitution|optimization|qualitative> \
  --current "<current state>" --target "<target state>" \
  --repos <svc-a,svc-b,svc-c> \
  --summary "<one line: the change>" \
  --model "{current model identifier}"
```

`--shape` defaults to `substitution`, so a technology retirement may omit it. An
optimization needs `--shape optimization` and a `metric` block; a qualitative
change needs `--shape qualitative` and an `invariant` block. The command refuses
a witness on the wrong shape, and refuses a non-substitution shape with no
witness at all — before the number is reserved.

The command applies every correction, records the replaced text as `as_was` on
each hub fact, re-registers the hash of every touched spec so the catalog asserts
the target representation on the same clock as the hub facts, records the shape's
witness, and writes one manifest at
`features/active/technical-improvement/IMP-NNN-{slug}/manifest.yml` at
`status: specified`.

**A branch is cut and you are switched onto it** — `imp/IMP-NNN-{slug}`, from the
integration branch. Report it. If the command says it *switched to* or *tracked* an
existing branch rather than cutting one, say so: its base is then whatever it was
originally created from.

**The number is claimed on `origin`**, locked by an `imp/NNNN` tag. A warning that
nothing was reserved (no remote, offline, or a repository that refuses tag pushes)
is a legal state, not a failure — report it and continue. `--force` skips the
reservation deliberately; reach for it only if the operator asks.

Read the output back, including every warning, and in particular the
**"Written, uncommitted"** list. This command corrects files all over the hub and
commits none of them.

## Step 8 -- Hand it to the code repos

Once the spec PR has merged:

```bash
ie imp handover IMP-NNN
```

Then `/ie/apply-improvement` in **each** repo — not `/ie/generate`, which
refuses an `IMP` manifest by name. `ie generation finalize` before each pull
request, as usual.

`ie imp deliver IMP-NNN` in the hub, last, and only once every repo named in
`affected_repos` carries its finalized archive on the integration branch. It
refuses until then, deliberately: a partially delivered migration is the state
this artifact exists to make visible.

It seals no use case and credits no promotion. A technology change demotes and
promotes no pattern, and the specs it touched were already implemented.
